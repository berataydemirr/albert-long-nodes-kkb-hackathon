# KKB data agent

This repo turns BDDK, EVDS and TUIK data into a small, queryable DuckDB
database, then lets an MIA model answer questions about it through a
tool-calling agent. The model plans; Python runs the tools and keeps the
data work local.

## Run it locally

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env
# add MIA_API_KEY to .env
.venv/bin/python -m src.gold.build_gold
.venv/bin/uvicorn web_app:app --reload
```

Open <http://127.0.0.1:8000>. The page shows ready-made prompts, the route a
request took, and every function call with its arguments and result. The
theme toggle in the header follows the OS setting by default and remembers
an explicit choice across reloads.

CLI equivalent:

```bash
.venv/bin/python agent.py "Konut kredisi faizi ile hacmi arasındaki ilişki nedir?"
```

## Tools

The router exposes every registered tool for a safe request, so one answer
can combine several:

- `lakehouse_schema`, `lakehouse_query` — inspect and query the read-only gold database
- `anomaly_analysis`, `change_detection` — find unusual points and sharp moves in a series
- `correlation_analysis`, `causality_analysis`, `threshold_filter_compare` — compare two series
- `compare_regions` — rank provinces across 35 lending, deposit and credit-quality metrics
- `list_imported_datasets`, `query_imported_dataset` — read a user-uploaded CSV/Excel/PDF table
- `refresh_tuik_series`, `search_tuik_dataflows` — re-fetch a registered TUIK series live, or search the full catalog for an unregistered one
- `fetch_bist_stock` — pull a BIST stock's live price history and store it
- `fuzzy_match_category` — reconcile a category name across sources that don't share a code
- `web_search`, `web_url_extract` — look up current public information and read a given URL

Analysis tools take a `seri_kod` and read the series from the database
themselves rather than having the model retype the numbers. `compare_regions`
covers 81 provinces and Yurt Dışı across 22 quarters; an unknown metric name
returns the full valid list instead of an error.

Answers that produce chartable numbers get a chart built from the tool
results, not generated by the model. Province rankings become horizontal
bars, series become lines, and two series are always drawn as two separate
charts rather than one plot with two axes. Every chart states its unit and
source and has a table view underneath.

Unsafe SQL or prompt-injection attempts are refused before the model is
given any tools.

## Data import

The upload button next to the message box (or `POST /api/upload`) accepts a CSV,
Excel, or PDF file up to 25 MB, detects its schema (column types inferred
column-by-column, not just pandas' default dtype guess), and loads it
directly into **lakehouse.duckdb** — the same file the curated `gold_*`
tables live in, in its own table named after the dataset. This is
deliberate: a table that lived in a second, isolated database file could
never be `JOIN`ed against the curated data, which defeats the point of
importing it in the first place. Two guarantees keep this safe instead:
a dataset name can never collide with a real `gold_*` table (rejected both
by a static prefix check and live against the connection's own table
list), and every imported table is tracked in `_import_registry` so it can
always be reported as user-supplied and unverified, unlike BDDK/EVDS/TUIK.
`list_imported_datasets` and `query_imported_dataset` are the direct way to
reach one; `lakehouse_query` can also reach it and `JOIN` it against a
`gold_*` table in the same query. All of this goes through the one shared
guardrail (`src/agent/sql_guard.py`) regardless of which tool is used.

PDF import (`src/agent/pdf_import.py`) uses `pdfplumber` — pure Python, no
Java/Ghostscript runtime required, unlike camelot or tabula. It finds
tables from actual ruling lines or aligned whitespace on the page; a
duplicate or blank extracted header column is rejected outright rather
than guessed at, since that's the most common sign the extraction actually
failed (usually a merged cell in the source table). A table split across
pages (identical header repeated) is detected and stitched into one import
by default. Every PDF import is returned with an explicit note to
spot-check values against the source page before relying on them.

### Data cleaning

Both import paths run the same pass (`src/agent/data_cleaning.py`) before
schema detection, and report every change back in a `data_quality` field
rather than applying anything silently:

- Turkish (`1.234,56`) vs. international (`2.009`) decimal notation, and
  abbreviated magnitudes (`1.5M`, `2,3 milyar`) — disambiguated per value,
  not per file, since a genuinely ambiguous case (a lone period followed by
  exactly 3 digits) cannot be resolved from the digits alone.
- Inconsistent null markers (`-`, `N/A`, `..`, a blank cell, an Excel
  formula error like `#REF!`) unified to one real null.
- Mixed date formats (ISO, `2023 1. Çeyrek`, `01-Mart-2023`) normalized to
  this project's `YYYY-MM` Period convention.
- A `Toplam`/subtotal row mixed into the same column as real observations,
  excluded rather than double-counted.
- A merged Excel header cell (a year spanning month sub-columns) recovered
  as real, distinct columns instead of pandas' `Unnamed: N` placeholders.
- Hidden Excel rows/columns excluded entirely, not imported as visible data.
- Mangled Turkish text from a wrong-codec round trip, repaired and verified
  (never trusted blindly) before being kept.

`fuzzy_match_category` reconciles a category name across sources that don't
share a code for it (BDDK's `Tarım, Avcılık ve Ormancılık` vs. TUIK's
`Tarım`) — a substring-aware `difflib` match, stdlib only.

`refresh_tuik_series` re-fetches an already-registered TUIK series
(currently the unemployment rate and life expectancy) live from TUIK's API
and writes the fresh values into `gold_fact_long`, tagged `Kaynak='tuik_live'`
(distinct from the batch-built `'tuik'` rows) so it stays identifiable while
being immediately queryable like any other series. It is deliberately
restricted to the existing registry in `config/tuik_series.py` rather than
accepting an arbitrary series key: TUIK's SDMX API addresses a series
through a multi-dimension key that has to be resolved by hand against that
dataflow's own codelists, so a model guessing one risks a wrong-but-real
series being reported as the one that was asked for.

`fetch_bist_stock` pulls live daily OHLCV price history for any BIST
(Borsa İstanbul) ticker from Yahoo Finance and writes it into the lakehouse
as `bist_<ticker>`. Unlike TUIK, this is not restricted to a pre-registered
list — a plain ticker symbol carries none of the SDMX key-resolution risk,
so any real BIST symbol works directly.

Two connections briefly wanting the same file — an import landing while a
`lakehouse_query` is mid-flight — is now possible where it wasn't with a
second file; DuckDB allows either N concurrent read-only connections or one
exclusive writer, never a mix, so a losing connection retries for up to
~2 seconds (`src/agent/db_utils.py`) rather than surfacing as a 500.

## Web search

The default provider, DuckDuckGo's public endpoint, returns a bot challenge
from some networks and may produce no results at all. The supported
alternative is a self-hosted, open-source SearXNG instance:

```bash
docker compose -f docker-compose.searxng.yml up -d
# then in .env: WEB_SEARCH_PROVIDER=searxng, SEARXNG_BASE_URL=http://localhost:8888
```

SearXNG queries around 70 backend engines at once, so one being blocked does
not take search down entirely. Its JSON API is off by default;
`searxng/settings.yml`, bind-mounted into the container, turns it on. Replace
the `secret_key` in that file before running the instance beyond localhost.
A blocked provider reports itself as unavailable rather than returning an
empty result list, so the model does not mistake a block for "no matches"
and keep retrying.

## Reliability

Each tool has its own call limit per answer. `web_search` and
`lakehouse_query` are capped at three, since repeated near-identical calls
usually signal a stuck model; analysis tools allow up to ten, since running
the same analysis across several series in one answer is ordinary use. An
identical repeat call is always refused.

If the model has not produced a final answer once the round budget is used
up, one more call is made with tools disabled, forcing a text answer from
whatever was already gathered. If that also fails, a short summary of the
tools that were tried is returned. No path raises an exception back to the
web server.

## Data layout

- `data/bronze/` — source responses
- `data/silver/` — cleaned CSVs
- `data/gold/lakehouse.duckdb` — analysis-ready tables, rebuilt locally
- `src/collectors/` — source downloads
- `src/processing/` — bronze to silver conversion
- `src/gold/` — silver to DuckDB build
- `src/agent/` — router, model loop and tools
- `docs/` — schema, routing and [agent architecture](docs/agent_architecture.md)

The gold build is network-free; it reads the checked-in silver files. The
collectors need the relevant source keys in `.env` and should be run with
care.

## Cost and speed

Wall time is almost entirely the model, not the data layer — tools took
0.66 s of a 32.4 s run. The model spends most of its time on reasoning
rather than the visible answer, so several things target that directly:

- The series catalog is injected into the system prompt, removing a round
  the model used to spend calling `lakehouse_schema` for the codes.
- Analysis tools read a series by its code instead of the model retyping it.
- The prompt bounds answer length and forbids repeating a tool call.
- `MIA_REASONING_EFFORT` (default `low`) controls how much the model
  thinks per call; tool selection and citation accuracy held steady across
  levels, so the cheaper settings do not trade accuracy for speed.

Together these cut a representative causality question from 32.4 s to 7.9 s.
Streaming was considered and not built, since the model emits nothing until
reasoning finishes — most of the wait happens before any text would appear.
Older tool outputs are replaced with short digests once the conversation
history passes a size budget, controlling cost without ever dropping a
message.

```bash
.venv/bin/python -m benchmarks.context_cost_benchmark       # local, no API calls
.venv/bin/python -m benchmarks.reasoning_effort_benchmark   # hits the API
```

Every run reports where its time and context went (`return_timing=True`,
also shown in the browser page).

## Checks

```bash
.venv/bin/python -m pytest -q
```

Tool calls and model rounds are written to `logs/`. Secrets, generated logs,
the virtual environment and the DuckDB file are ignored by Git.

## Edge-case benchmark

```bash
.venv/bin/python -m benchmarks.hard_benchmark              # full run, ~20 min
.venv/bin/python -m benchmarks.hard_benchmark --category adversarial
```

`benchmarks/hard_benchmark.py` runs a curated set of adversarial and
edge-case questions against the real API across 24 categories (multi-hop
chains, extreme and malformed parameters, missing-data admission, prompt
injection including unicode/base64-obfuscated variants, batch and
loop-guard stress, BIST/TUIK live fetches, TUIK dataflow discovery,
PDF-import questions against a synthetic fixture, SQL guardrail edge
cases, province-name typos/case variants, unit/scale traps, long
rambling and mixed-language phrasing, numeric-grounding stress, deep
regional comparisons, internal-consistency and methodology-transparency
questions) and tracks the things the team asked to have tracked:
tool-selection accuracy, numeric grounding (does a number the model
wrote trace back to a number a tool actually returned - see below),
consistency (three repeat runs of three questions, compared), speed
(per-question, average, median and max latency), a hallucinated-series/
dataset-name rate, missing-data admission rate, and guardrail/DDL-
attempt-blocked rate. Two small, explicitly-synthetic fixtures
(`benchmark_synthetic_csv`/`_pdf`) are imported automatically before each
run so the import-related questions have something real and known to
query. Results are written to `benchmarks/hard_benchmark_report.json`,
per-question and aggregated. It is 153 questions, not the 150-200
originally asked for — each one targets a distinct failure mode rather
than padding the count with variations of the same question; the harness
(`BENCHMARK_QUESTIONS`) takes one dictionary entry to extend.

**Numeric grounding.** Tool-selection accuracy alone does not prove an
answer's own numbers are real - the right tool can be called, return a
correct result, and the model can still misreport it in prose. Every
decimal number in an answer is checked against what the tool calls in
that answer's trace actually returned, including simple derived
arithmetic (percent/decimal conversion, squaring for r², a ratio for a
currency conversion, a Bin/Milyon/Milyar TL scale change, rounding to
fewer decimal places). It is a heuristic, not a hard gate - genuinely
ambiguous Turkish number notation (`9.268` could be the thousands-grouped
integer 9268 or the decimal 9.268; both readings are offered and either
counts as grounded) - so every "ungrounded" number is kept in the report
for manual review rather than silently failing the question. Every case
found this way during development turned out to be a gap in the checker
itself, not a real fabrication - each was manually confirmed and folded
back into the derived-arithmetic rules above.
